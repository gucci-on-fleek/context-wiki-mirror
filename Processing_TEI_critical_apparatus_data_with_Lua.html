A TEI document can describe witnesses, lemmas, variant readings, omissions, additions, editorial interventions, and the relationships between these elements. ConTeXt can subsequently use this information to produce a typographically structured critical apparatus.

A direct passage from XML elements to printed output is possible in very simple cases. It becomes increasingly fragile, however, when the source contains multiple witnesses, abbreviated references, several kinds of readings, incomplete records, or editorial conventions that must be applied consistently.

Lua provides an intermediate processing layer between the documentary structure of TEI and the typographical structure produced by ConTeXt.

Its role is not limited to reading XML. Lua can:

  • collect declarations from different parts of the TEI document;
  • transform XML elements into consistent internal records;
  • normalize identifiers, witness lists, and textual values;
  • resolve references such as #A or #B ;
  • verify that the referenced objects have actually been declared;
  • distinguish usable data from incomplete or contradictory data;
  • prepare a stable representation that ConTeXt can typeset.

This guide develops that intermediate layer. It stops before the final composition of the critical apparatus. The records produced here will be passed to ConTeXt in the next guide.

1. What this guide does

The examples in this guide progressively construct a small processing system for TEI critical apparatus data.

The system will:

  1. build a registry of textual witnesses;
  2. convert TEI apparatus entries into Lua records;
  3. resolve witness references against the registry;
  4. validate the resulting records;
  5. report errors and warnings;
  6. make the validated records available to ConTeXt.

The aim is not to reproduce the whole TEI specification in Lua. Nor is it to replace TEI with a second and competing data model.

The Lua representation is deliberately smaller than the XML source. It retains the information required by the current editorial and typographical task while preserving links to the TEI elements from which that information was derived.

Guiding principle. TEI remains the documentary source, Lua constructs and checks task-oriented editorial records, and ConTeXt gives those records their typographical form. The three layers cooperate, but they do not have the same responsibility.

2. Why use Lua between TEI and ConTeXt?

2.1. Reading is not yet interpreting

Reading an XML element answers questions such as:

  • What is the name of this element?
  • Which attributes does it possess?
  • What text does it contain?
  • Where does it occur in the document?

These are necessary questions, but they are not sufficient for producing a critical edition.

Suppose that a TEI reading contains: 

<rdg wit="#A #C">λόγος</rdg>

The XML parser can return the string #A #C. It has not yet established:

  • that this string contains two witness references;
  • that the leading number signs are reference markers rather than parts of the identifiers;
  • that witnesses A and C have been declared;
  • that both witnesses are admissible in the current apparatus;
  • that their order should be preserved or normalized;
  • that the same witness has not accidentally been listed twice.

The parser exposes the encoded data. Lua determines how that data is to be understood within the editorial workflow.

This distinction is fundamental. XML parsing produces access to a document structure. Editorial processing produces knowledge about the consistency and meaning of the encoded relationships.

2.2. Normalizing editorial data

Equivalent information may appear in several surface forms.

For example, witness references might be written as: 

wit="#A #B"
wit=" #A   #B "
wit="#A #A #B"

Depending on the rules adopted for the edition, these values may need to be converted into the same internal representation: 

{ "A", "B" }

Normalization may include:

  • removing reference markers;
  • trimming insignificant whitespace;
  • splitting a list into individual identifiers;
  • removing accidental duplicates;
  • preserving or standardizing witness order;
  • replacing absent values with explicit Lua values;
  • converting XML strings into booleans, numbers, or controlled categories.

Normalization does not merely make the data more convenient to program. It establishes which differences in the source are editorially significant and which are only differences of notation.

Lua therefore participates in the definition of equivalence between encoded forms.

2.3. Resolving references

TEI commonly represents relationships by identifiers and references.

A witness may be declared in a <listWit>: 

<witness xml:id="A">Paris, Bibliothèque nationale de France, grec 1807</witness>

An apparatus entry may refer to it elsewhere: 

<rdg wit="#A">...</rdg>

The apparatus entry does not itself contain the witness description. It contains a reference to a declared object.

Lua can resolve this reference by consulting a witness registry: 

witnesses["A"]

The result can provide the siglum, description, type, group, order, or any other information required later by the edition.

Reference resolution changes the status of the data. Before resolution, #A is a character string. After successful resolution, it denotes a known witness record. If no such record exists, the reference becomes a detectable editorial problem.

2.4. Validating the editorial model

A document can be well-formed XML and still contain unusable critical data.

For example:

  • a reading may refer to an undeclared witness;
  • an apparatus entry may contain no lemma;
  • a witness identifier may be declared twice;
  • a reading may contain neither text nor an omission marker;
  • the same witness may be assigned incompatible readings;
  • a required classification may be absent;
  • a reference may be syntactically valid but editorially inappropriate.

An XML parser does not normally treat these conditions as parsing errors. They concern the editorial model rather than the syntax of XML.

Lua allows the edition to express these additional constraints explicitly.

Validation can produce different levels of diagnostic information:

  • an error identifies data that cannot safely be processed;
  • a warning identifies data that may be intentional but deserves review;
  • an informational message records a normalization or an editorial choice.

The purpose of validation is not merely to reject malformed input. It makes the assumptions of the edition visible and testable.

Important. Well-formed XML is not necessarily editorially usable XML. Syntax can be correct while witness references, classifications, or apparatus relationships remain incomplete or contradictory.

2.5. Separating interpretation from typesetting

Without an intermediate layer, typographical commands can become responsible for too many tasks at once. A ConTeXt macro may then have to:

  • read an XML attribute;
  • split a witness list;
  • remove reference markers;
  • check declarations;
  • decide how omissions are represented;
  • determine punctuation;
  • sort sigla;
  • and finally typeset the apparatus entry.

Such a macro mixes documentary interpretation, editorial policy, error handling, and visual presentation.

The separation adopted in this guide is more robust: 

TEI XML
    ↓
Lua interpretation and validation
    ↓
validated Lua records
    ↓
ConTeXt typesetting

Lua answers questions such as:

  • What does this apparatus entry contain?
  • Which witnesses does it concern?
  • Are its references valid?
  • Which normalized values should be passed forward?

ConTeXt answers a different set of questions:

  • Where should the apparatus appear?
  • How should the lemma be distinguished?
  • How should witnesses be separated?
  • Which font, spacing, punctuation, or paragraph structure should be used?

The boundary is not absolute, but it provides a useful principle: Lua should prepare editorially meaningful records; ConTeXt should transform those records into pages.

Division of labour. Lua answers questions about identity, structure, consistency, and editorial status. ConTeXt answers questions about placement, visual hierarchy, spacing, punctuation, and page construction.

3. The processing pipeline

The complete workflow developed in this guide consists of several distinct stages.

Stage Input Operation Result
1. Documentary encoding TEI elements and attributes The editor records witnesses, lemmas, readings, and relationships. A structured XML document
2. Extraction TEI XML Lua selects the elements and attributes relevant to the apparatus. Raw Lua values
3. Normalization Raw strings and element content Lua trims, splits, classifies, and standardizes the values. Consistent Lua fields
4. Reference resolution Identifiers such as #A Lua connects references with declared witness records. Resolved editorial objects
5. Validation Normalized and resolved records Lua tests structural and editorial constraints. Errors, warnings, and usable records
6. Intermediate representation Validated apparatus data Lua stores the information in a stable internal form. Records prepared for ConTeXt
7. Typesetting Validated Lua records ConTeXt applies the required typographical structure. The printed or electronic apparatus

These stages should not be confused with the chronological actions of a single program. A practical implementation may combine several operations in one Lua function.

The conceptual distinctions nevertheless remain important. They make it possible to determine where a particular decision belongs and where a particular error should be reported.

3.1. TEI as the documentary source

TEI remains the authoritative documentary representation.

It records the textual evidence and preserves distinctions that may be useful for purposes beyond the immediate ConTeXt output. The Lua layer should not silently rewrite the TEI source or discard distinctions merely because they are not currently displayed.

Where possible, each Lua record should retain the identifier of its source TEI element. This makes it easier to relate a diagnostic message or a typeset entry to the original encoding.

3.2. Lua as the interpretative layer

Lua receives XML structures but produces editorial objects.

A witness record may contain fields such as: 

{
    id          = "A",
    siglum      = "A",
    description = "Paris, Bibliothèque nationale de France, grec 1807",
    kind        = "manuscript",
    order       = 1,
}

An apparatus record may contain: 

{
    id       = "app-001",
    lemma    = "λόγος",
    readings = {
        {
            text      = "λέξις",
            witnesses = { "B", "C" },
        },
    },
    valid = true,
}

These tables are not substitutes for TEI. They are task-oriented representations constructed from TEI.

Their structure reflects what the next stage of the workflow needs to know.

3.3. Validated records as an intermediate representation

The intermediate representation provides a contract between data processing and typesetting.

The processing layer guarantees, for example, that:

  • every witness identifier has a normalized form;
  • every resolved witness exists in the registry;
  • every apparatus record has a predictable structure;
  • absent information is represented explicitly;
  • invalid records are marked or excluded;
  • diagnostic messages have already been produced.

The typesetting layer can therefore operate on records rather than repeatedly interpreting XML syntax.

This intermediate representation is also useful for purposes other than typesetting. The same records can support:

  • editorial reports;
  • lists of undeclared witnesses;
  • witness statistics;
  • indexes of variant locations;
  • consistency checks;
  • alternative output formats;
  • automated tests.

3.4. ConTeXt as the typesetting layer

ConTeXt receives records whose editorial meaning has already been established.

It can then concentrate on presentation:

  • converting a record into an apparatus note;
  • applying the selected lemma and reading styles;
  • formatting sigla;
  • placing entries in one or more apparatus layers;
  • controlling line breaking and page breaking;
  • producing references and navigation;
  • adapting the same data to print or screen output.

The final typographical composition belongs to Guide 6.

The examples that follow therefore display the constructed records and validation reports, but they do not yet create the final critical apparatus.

4. Building a witness registry from TEI XML

Before an apparatus entry can be interpreted, the witnesses to which it refers must be known.

TEI normally declares textual witnesses in a <listWit> element. Each <witness> receives an identifier that may later be referenced from a lemma or a reading.

For example: 

<listWit>
  <witness xml:id="A" type="manuscript">
    Paris, Bibliothèque nationale de France, grec 1807
  </witness>
  <witness xml:id="B" type="manuscript">
    Vatican City, Biblioteca Apostolica Vaticana, Vat. gr. 1
  </witness>
  <witness xml:id="C" type="edition">
    Aldine edition, Venice, 1513
  </witness>
</listWit>

At the XML level, these are three document elements. For subsequent processing, Lua needs a registry in which each identifier gives direct access to a structured witness record.

The intended result has the following general form: 

witnesses["A"] = {
    id          = "A",
    siglum      = "A",
    kind        = "manuscript",
    description = "Paris, Bibliothèque nationale de France, grec 1807",
    order       = 1,
}

The registry does more than reproduce the XML declarations. It establishes a controlled collection of known editorial objects.

4.1. The TEI witness declarations

A witness declaration can supply several kinds of information:

  • an identifier used by internal references;
  • a siglum displayed in the apparatus;
  • a description of the manuscript, edition, or source;
  • a classification such as manuscript or edition ;
  • an order used when witnesses are displayed or compared.

Not every edition will require all these fields. The Lua registry should retain only the information needed by the processing and typesetting workflow.

The identifier is nevertheless essential. Without it, later references such as wit="#A" cannot be resolved reliably.

In this first example, the siglum is derived from xml:id. A later project could instead read the displayed siglum from an additional TEI element or attribute.

4.2. Constructing the Lua registry

The registry uses two complementary Lua structures: 

witnesses.by_id
witnesses.in_order

The first provides direct lookup by identifier: 

witnesses.by_id["A"]

The second preserves the order in which witnesses were declared: 

witnesses.in_order[1]

Maintaining both structures avoids a common ambiguity. A Lua table indexed by identifiers is suitable for reference resolution, but it should not be relied upon to preserve an editorially significant sequence.

During construction, the processing code checks that:

  • every witness has an identifier;
  • no identifier is declared more than once;
  • textual descriptions are normalized;
  • the documentary order is recorded explicitly.

A missing identifier and a duplicate identifier are treated as errors because they prevent unambiguous reference resolution.

4.3. Looking up witness information

Once the registry has been constructed, later processing stages no longer need to search the original <listWit> repeatedly.

They can request a witness directly: 

local witness = witnesses.by_id["B"]

If the lookup succeeds, witness denotes a complete record. If it fails, the requested identifier has not been declared in the registry.

This distinction will become important when apparatus entries are validated.

A reference such as: 

<rdg wit="#A #B">λέξις</rdg>

will eventually be converted into a list of normalized identifiers: 

{ "A", "B" }

Each identifier can then be checked against: 

witnesses.by_id

4.4. Functional MWE: Building a witness registry from TEI XML

The following example reads witness declarations from a TEI fragment, builds a Lua registry, records errors, and prints a diagnostic report.

It does not yet process apparatus entries. Its sole purpose is to establish the collection of witnesses against which later references will be resolved. 

\mainlanguage[en]

\setuppapersize[A5]

\setupbodyfont
  [libertinus,10pt]

\setupwhitespace
  [medium]

\startbuffer[tei-data]
<TEI>
  <text>
    <body>
      <listWit>
        <witness xml:id="A" type="manuscript">
          Paris, Bibliothèque nationale de France, grec 1807
        </witness>

        <witness xml:id="B" type="manuscript">
          Vatican City, Biblioteca Apostolica Vaticana, Vat. gr. 1
        </witness>

        <witness xml:id="C" type="edition">
          Aldine edition, Venice, 1513
        </witness>
      </listWit>
    </body>
  </text>
</TEI>
\stopbuffer

\startluacode

thirddata = thirddata or {}

thirddata.tei_witnesses = {
    by_id    = {},
    in_order = {},
    errors   = {},
}

local registry = thirddata.tei_witnesses

local function normalize_space(value)
    if not value then
        return ""
    end

    value = value:gsub("%s+", " ")
    value = value:gsub("^%s+", "")
    value = value:gsub("%s+$", "")

    return value
end

local function add_error(message)
    registry.errors[#registry.errors + 1] = message
end

local function reset_registry()
    registry.by_id    = {}
    registry.in_order = {}
    registry.errors   = {}
end

local function register_witness(node)
    local attributes = node.at or {}

    local id =
        attributes["xml:id"]
        or attributes.id
        or ""

    local kind =
        attributes.type
        or ""

    id   = normalize_space(id)
    kind = normalize_space(kind)

    local description =
        normalize_space(xml.text(node))

    if id == "" then
        add_error(
            "A witness declaration has no xml:id."
        )
        return
    end

    if registry.by_id[id] then
        add_error(
            "Duplicate witness identifier: " .. id
        )
        return
    end

    local record = {
        id          = id,
        siglum      = id,
        kind        = kind ~= "" and kind or "unspecified",
        description = description,
        order       = #registry.in_order + 1,
        source      = node,
    }

    registry.by_id[id] = record
    registry.in_order[#registry.in_order + 1] = record
end

function registry.build()
    reset_registry()

    local document = xml.convert(
        buffers.getcontent("tei-data")
    )

    for node in xml.collected(
        document,
        "witness"
    ) do
        register_witness(node)
    end
end

function registry.lookup(id)
    return registry.by_id[id]
end

function registry.typeset()
    context.subject("Witness registry")

    context.starttabulate {
        "|l|l|p|"
    }

    context.NC()
    context.bold("Siglum")
    context.NC()
    context.bold("Kind")
    context.NC()
    context.bold("Description")
    context.NC()
    context.NR()

    for _, witness in ipairs(registry.in_order) do
        context.NC()
        context(witness.siglum)

        context.NC()
        context(witness.kind)

        context.NC()
        context(witness.description)

        context.NC()
        context.NR()
    end

    context.stoptabulate()

    context.blank()

    context.subject("Lookup test")

    local selected = registry.lookup("B")

    if selected then
        context(
            "Witness B is registered as a %s.",
            selected.kind
        )
    else
        context(
            "Witness B is not registered."
        )
    end

    context.blank()

    context.subject("Registry report")

    context(
        "Registered witnesses: %s",
        #registry.in_order
    )

    context.par()

    if #registry.errors == 0 then
        context(
            "No registry errors were detected."
        )
    else
        context(
            "Errors: %s",
            #registry.errors
        )

        context.startitemize()

        for _, message in ipairs(registry.errors) do
            context.startitem()
            context(message)
            context.stopitem()
        end

        context.stopitemize()
    end
end

The central result of the example is not the table printed on the page. The important result is the Lua registry itself: 

witnesses.by_id
witnesses.in_order
witnesses.errors

These three fields represent different kinds of knowledge about the TEI document:

  • by_id records which witnesses are known and makes them 
 directly accessible;
  • in_order records the sequence in which the witnesses were 
 declared;
  • errors records conditions that prevent reliable interpretation.

The source XML contains witness declarations. The Lua registry turns those declarations into a collection of identifiable, ordered, and verifiable editorial objects.

4.5. Testing missing and duplicate identifiers

The validation behaviour can be tested by adding the following declarations to the TEI buffer: 

<witness type="manuscript">
  An unidentified manuscript
</witness>

<witness xml:id="A" type="manuscript">
  A second declaration using the identifier A
</witness>

The first declaration cannot be referenced because it has no xml:id. The second makes the identifier A ambiguous because that identifier is already present in the registry.

The processing layer therefore reports both conditions and excludes the problematic declarations from the usable registry.

This is an important difference between merely traversing the XML tree and constructing an editorial representation. Traversal can find both elements. Registry construction must decide whether they can function as stable objects within the edition.

4.6. Result of this stage

At the end of this stage, Lua possesses a witness registry with the following properties:

  • every usable witness has a unique normalized identifier;
  • every identifier gives access to a structured record;
  • documentary order is preserved separately from identifier lookup;
  • incomplete and duplicate declarations are reported;
  • later apparatus references can be checked against a known set of witnesses.

The next stage will use this registry while converting <app>, <lem>, and <rdg> elements into Lua apparatus records.

5. Converting TEI apparatus entries into Lua records

Once the witness registry has been constructed, the apparatus entries themselves can be processed.

A TEI apparatus entry normally groups a lemma with one or more variant readings: 

<app xml:id="app-001">
  <lem wit="#A">λόγος</lem>
  <rdg wit="#B #C">λέξις</rdg>
</app>

At the XML level, this structure records a textual relationship. It identifies the lemma, the alternative reading, and the witnesses associated with each form.

For later processing, Lua converts the XML elements into a predictable record: 

{
    id = "app-001",

    lemma = {
        text      = "λόγος",
        witnesses = { "A" },
    },

    readings = {
        {
            text      = "λέξις",
            witnesses = { "B", "C" },
            kind      = "reading",
        },
    },

    valid = true,
}

This transformation does not yet typeset the apparatus entry. It establishes an intermediate representation in which textual content, witness references, and editorial categories are separated into explicit fields.

5.1. Reading lemmas and variant readings

The <app> element acts as a container. Its children provide the editorial content that must be interpreted.

The principal elements used in this example are:

  • <lem> , which records the lemma;
  • <rdg> , which records a variant reading;
  • @wit , which associates a lemma or reading with one or more 
 witnesses;
  • @xml:id , which gives the apparatus entry a stable identifier.

A single apparatus entry may contain several <rdg> elements: 

<app xml:id="app-002">
  <lem wit="#A">ἀλήθεια</lem>
  <rdg wit="#B">ἀληθεία</rdg>
  <rdg wit="#C">ἀλήθειαν</rdg>
</app>

The corresponding Lua record therefore stores the readings in an ordered array: 

readings = {
    {
        text      = "ἀληθεία",
        witnesses = { "B" },
    },
    {
        text      = "ἀλήθειαν",
        witnesses = { "C" },
    },
}

The order of the readings may be significant. It should therefore be preserved explicitly rather than reconstructed later from an unordered table.

5.2. Normalizing witness lists

The value of a TEI @wit attribute is a whitespace-separated list of references: 

wit="#B #C"

Lua must convert this string into individual identifiers: 

{ "B", "C" }

The normalization operation performs several tasks:

  • removes the leading # reference marker;
  • ignores insignificant whitespace;
  • separates the references;
  • removes accidental duplicates;
  • preserves the order of first occurrence.

For example: 

wit="  #B   #C  #B "

becomes: 

{ "B", "C" }

This operation establishes that differences in spacing and repeated references do not create distinct witness lists.

The normalized identifiers are not yet guaranteed to be valid. They will be checked against the witness registry in section 6.

5.3. Preserving editorial distinctions

Not every <rdg> contains an ordinary replacement reading.

TEI can represent several editorial situations, including:

  • a textual variant;
  • an omission;
  • an addition;
  • an orthographic form;
  • a conjecture;
  • a reading attributed to a particular source or hand.

The Lua record should therefore retain an explicit category rather than infer the meaning later from the displayed text.

A normal reading may be represented as: 

{
    kind      = "reading",
    text      = "λέξις",
    witnesses = { "B", "C" },
}

An omission may be represented as: 

{
    kind      = "omission",
    text      = "",
    witnesses = { "C" },
}

This distinction is important because an empty textual value does not by itself explain why the text is absent. It may represent an omission, missing data, or an encoding error.

The TEI source must therefore supply enough information for Lua to distinguish these cases.

In the following MWE, the attribute type="omission" is used to identify an omission explicitly: 

<rdg wit="#C" type="omission"/>

The Lua processing layer preserves this distinction in the kind field.

5.4. Functional MWE: Converting TEI apparatus entries into Lua records

The following example extends the witness-registry mechanism developed in section 4.

It reads two apparatus entries, normalizes their witness lists, preserves the order of their readings, and constructs Lua records.

The example displays the resulting records for inspection. It does not yet validate whether every witness reference is known. 

\mainlanguage[en]

\setuppapersize[A5]

\setupbodyfont
  [libertinus,10pt]

\setupwhitespace
  [medium]

\startbuffer[tei-data]
<TEI>
  <text>
    <body>

      <listWit>
        <witness xml:id="A" type="manuscript">
          Paris, Bibliothèque nationale de France, grec 1807
        </witness>

        <witness xml:id="B" type="manuscript">
          Vatican City, Biblioteca Apostolica Vaticana, Vat. gr. 1
        </witness>

        <witness xml:id="C" type="edition">
          Aldine edition, Venice, 1513
        </witness>
      </listWit>

6. Validating witness references and apparatus records

The apparatus records constructed in section 5 have a predictable Lua structure, but their internal consistency has not yet been established.

Normalization can transform: 

wit=" #B  #C "

into: 

{ "B", "C" }

It cannot determine by itself whether witnesses B and C have actually been declared.

Validation introduces this additional stage. It compares the apparatus records with the witness registry and tests rules that concern the editorial model rather than XML syntax.

A record may therefore be structurally readable while remaining editorially invalid.

6.1. Detecting unknown witnesses

Each normalized witness identifier must be resolved against the registry constructed from <listWit>.

For example: 

<rdg wit="#B #D">λέξις</rdg>

may be converted into: 

{ "B", "D" }

If only witness B has been declared, the identifier D remains unresolved.

Lua can detect this condition by consulting: 

registry.by_id["D"]

An unresolved reference is treated as an error because the processing layer cannot determine which editorial object the identifier is intended to denote.

The diagnostic message should identify both:

  • the apparatus record in which the problem occurs;
  • the unresolved witness identifier.

For example: 

app-002: unknown witness D in reading 1.

This makes it possible to trace the problem back to a specific part of the TEI source.

6.2. Detecting incomplete apparatus entries

An apparatus entry may be valid XML while lacking information required by the edition.

Possible problems include:

  • an <app> element without a lemma;
  • a lemma without textual content;
  • an apparatus entry without readings;
  • an ordinary reading with no text;
  • an omission that has not been explicitly classified;
  • a witness list that is absent where the editorial model requires one.

These conditions cannot all be inferred from XML well-formedness.

For example: 

<app xml:id="app-003">
  <rdg wit="#B">λέξις</rdg>
</app>

is well-formed XML, but the apparatus record has no lemma.

Likewise: 

<rdg wit="#C"/>

contains no text. Without an explicit category such as: 

type="omission"

the processing layer cannot know whether the empty content represents an intentional omission or incomplete data.

Validation therefore tests not only the presence of elements, but also the relationship between their textual content and their editorial classification.

6.3. Distinguishing errors from warnings

Not every irregularity makes a record unusable.

This guide distinguishes two principal diagnostic levels.

An error identifies a condition that prevents safe interpretation, such as:

  • an unknown witness;
  • a missing lemma;
  • an empty ordinary reading;
  • an ambiguous duplicate witness declaration.

A warning identifies a condition that can be normalized or may be intentional, but should remain visible to the editor, such as:

  • a witness repeated in the same @wit value;
  • an apparatus entry with no variant readings;
  • an omission element that unexpectedly contains text;
  • an automatically generated apparatus identifier.

This distinction prevents validation from becoming a simple choice between acceptance and rejection.

A record may remain usable while carrying warnings that deserve editorial review.

The diagnostics are therefore part of the intermediate representation. They record not only whether processing succeeded, but also which interpretative decisions were required.

local function normalize_space(value)

        return ""
    end

    value = value:gsub("%s+", " ")

    value = value:gsub("%s+$", "")

    return value
end

local function add_error(message)
    validation.errors[#validation.errors + 1] = message
end

local function add_warning(message)
    validation.warnings[#validation.warnings + 1] = message
end

local function normalize_witnesses(value)
    local result     = {}
    local seen       = {}
    local duplicates = {}

    value = normalize_space(value)

    for reference in value:gmatch("%S+") do
        local id = reference:gsub("^#", "")

        if id ~= "" then
            if seen[id] then
                duplicates[#duplicates + 1] = id
            else
                result[#result + 1] = id
                seen[id] = true
            end
        end
    end

    return result, duplicates
end

local function build_witness_registry(document)
    validation.witnesses.by_id    = {}
    validation.witnesses.in_order = {}

    for node in xml.collected(document, "witness") do
        local attributes = node.at or {}

        local id =
            normalize_space(
                attributes["xml:id"]
                or attributes.id
            )

        if id == "" then
            add_error(
                "A witness declaration has no xml:id."
            )
        elseif validation.witnesses.by_id[id] then
            add_error(
                "Duplicate witness identifier: " .. id
            )
        else
            local record = {
                id          = id,
                siglum      = id,
                kind        =
                    normalize_space(attributes.type)
                    ~= ""
                    and normalize_space(attributes.type)
                    or "unspecified",
                description =
                    normalize_space(xml.text(node)),
                order       =
                    #validation.witnesses.in_order + 1,
                source      = node,
            }

            validation.witnesses.by_id[id] = record

            validation.witnesses.in_order[
                #validation.witnesses.in_order + 1
            ] = record
        end
    end
end

local function make_text_record(node, default_kind)
    if not node then
        return nil
    end

    local attributes = node.at or {}

    local witnesses, duplicates =
        normalize_witnesses(attributes.wit)

    local kind =
        normalize_space(attributes.type)

    if kind == "" then
        kind = default_kind
    end

    return {
        kind       = kind,
        text       = normalize_space(xml.text(node)),
        witnesses  = witnesses,
        duplicates = duplicates,
        source     = node,
    }
end

local function build_apparatus_records(document)
    validation.records = {}

    local position = 0

    for node in xml.collected(document, "app") do
        position = position + 1

        local attributes = node.at or {}

        local id =
            normalize_space(
                attributes["xml:id"]
                or attributes.id
            )

        if id == "" then
            id = "app-" .. position

            add_warning(
                id .. ": generated identifier."
            )
        end

        local record = {
            id       = id,
            lemma    =
                make_text_record(
                    xml.first(node, "lem"),
                    "lemma"
                ),
            readings = {},
            order    = position,
            source   = node,
            valid    = true,
        }

        for reading_node in xml.collected(node, "rdg") do
            record.readings[#record.readings + 1] =
                make_text_record(
                    reading_node,
                    "reading"
                )
        end

        validation.records[
            #validation.records + 1
        ] = record
    end
end

local function validate_witness_list(
    record,
    list,
    location
)
    for _, id in ipairs(list) do
        if not validation.witnesses.by_id[id] then
            add_error(
                string.format(
                    "%s: unknown witness %s in %s.",
                    record.id,
                    id,
                    location
                )
            )

            record.valid = false
        end
    end
end

local function report_duplicates(
    record,
    duplicates,
    location
)
    for _, id in ipairs(duplicates) do
        add_warning(
            string.format(
                "%s: duplicate witness %s in %s; "
                .. "the repeated reference was removed.",
                record.id,
                id,
                location
            )
        )
    end
end

local function validate_record(record)
    if not record.lemma then
        add_error(
            record.id .. ": missing lemma."
        )

        record.valid = false
    else
        if record.lemma.text == "" then
            add_error(
                record.id .. ": the lemma is empty."
            )

            record.valid = false
        end

        validate_witness_list(
            record,
            record.lemma.witnesses,
            "lemma"
        )

        report_duplicates(
            record,
            record.lemma.duplicates,
            "lemma"
        )
    end

    if #record.readings == 0 then
        add_warning(
            record.id .. ": no variant readings."
        )
    end

    for index, reading in ipairs(record.readings) do
        local location =
            "reading " .. index

        validate_witness_list(
            record,
            reading.witnesses,
            location
        )

        report_duplicates(
            record,
            reading.duplicates,
            location
        )

        if reading.kind == "omission" then
            if reading.text ~= "" then
                add_warning(
                    string.format(
                        "%s: %s is classified as an "
                        .. "omission but contains text.",
                        record.id,
                        location
                    )
                )
            end
        elseif reading.text == "" then
            add_error(
                string.format(
                    "%s: %s is empty and is not "
                    .. "classified as an omission.",
                    record.id,
                    location
                )
            )

            record.valid = false
        end
    end
end

function validation.build()
    validation.errors   = {}
    validation.warnings = {}
    validation.records  = {}

    local document = xml.convert(
        buffers.getcontent("tei-data")
    )

    build_witness_registry(document)
    build_apparatus_records(document)

    for _, record in ipairs(validation.records) do
        validate_record(record)
    end
end

local function typeset_status(record)
    if record.valid then
        context("valid")
    else
        context("invalid")
    end
end

    processing.accepted           = {}
    processing.errors             = {}
    processing.warnings           = {}
end

local function normalize_witnesses(value)
    local identifiers = {}
    local duplicates  = {}
    local seen        = {}

    value = normalize_space(value)

    for reference in value:gmatch("%S+") do
        local id =
            reference:gsub("^#", "")

        if id ~= "" then
            if seen[id] then
                duplicates[
                    #duplicates + 1
                ] = id
            else
                identifiers[
                    #identifiers + 1
                ] = id

                seen[id] = true
            end
        end
    end

    return identifiers, duplicates
end

local function build_witness_registry(document)
    for node in xml.collected(
        document,
        "witness"
    ) do
        local attributes = node.at or {}

        local id =
            normalize_space(
                attributes["xml:id"]
                or attributes.id
            )

        if id == "" then
            add_global_error(
                "A witness declaration has no xml:id."
            )
        elseif processing.witnesses.by_id[id] then
            add_global_error(
                "Duplicate witness identifier: " .. id
            )
        else
            local kind =
                normalize_space(
                    attributes.type
                )

            local record = {
                id          = id,
                siglum      = id,
                kind        =
                    kind ~= ""
                    and kind
                    or "unspecified",
                description =
                    normalize_space(
                        xml.text(node)
                    ),
                order       =
                    #processing.witnesses.in_order + 1,
                source      = node,
            }

            processing.witnesses.by_id[id] =
                record

            processing.witnesses.in_order[
                #processing.witnesses.in_order + 1
            ] = record
        end
    end
end

local function make_text_record(
    node,
    default_kind
)
    if not node then
        return nil
    end

    local attributes = node.at or {}

    local witness_ids, duplicates =
        normalize_witnesses(
            attributes.wit
        )

    local kind =
        normalize_space(
            attributes.type
        )

    if kind == "" then
        kind = default_kind
    end

    return {
        kind        = kind,
        text        =
            normalize_space(
                xml.text(node)
            ),
        witness_ids = witness_ids,
        witnesses   = {},
        duplicates  = duplicates,
        valid       = true,
        source      = node,
    }
end

local function build_apparatus_records(document)
    local position = 0

    for node in xml.collected(
        document,
        "app"
    ) do
        position = position + 1

        local attributes = node.at or {}

        local id =
            normalize_space(
                attributes["xml:id"]
                or attributes.id
            )

        local generated_id = false

        if id == "" then
            id = "app-" .. position
            generated_id = true
        end

        local record = {
            id       = id,
            lemma    =
                make_text_record(
                    xml.first(node, "lem"),
                    "lemma"
                ),
            readings = {},
            order    = position,
            valid    = true,
            errors   = {},
            warnings = {},
            source   = node,
        }

        if generated_id then
            add_record_warning(
                record,
                "generated apparatus identifier."
            )
        end

        for reading_node in xml.collected(
            node,
            "rdg"
        ) do
            record.readings[
                #record.readings + 1
            ] = make_text_record(
                reading_node,
                "reading"
            )
        end

        processing.records[
            #processing.records + 1
        ] = record
    end
end

local function resolve_witnesses(
    record,
    text_record,
    location
)
    text_record.witnesses = {}

    for _, id in ipairs(
        text_record.witness_ids
    ) do
        local witness =
            processing.witnesses.by_id[id]

        if witness then
            text_record.witnesses[
                #text_record.witnesses + 1
            ] = witness
        else
            text_record.valid = false

            add_record_error(
                record,
                string.format(
                    "unknown witness %s in %s.",
                    id,
                    location
                )
            )
        end
    end

    for _, id in ipairs(
        text_record.duplicates
    ) do
        add_record_warning(
            record,
            string.format(
                "duplicate witness %s in %s; "
                .. "the repeated reference was removed.",
                id,
                location
            )
        )
    end
end

local function validate_record(record)
    if not record.lemma then
        add_record_error(
            record,
            "missing lemma."
        )
    else
        if record.lemma.text == "" then
            add_record_error(
                record,
                "the lemma is empty."
            )
        end

        resolve_witnesses(
            record,
            record.lemma,
            "lemma"
        )
    end

    if #record.readings == 0 then
        add_record_warning(
            record,
            "no variant readings."
        )
    end

    for index, reading in ipairs(
        record.readings
    ) do
        local location =
            "reading " .. index

        resolve_witnesses(
            record,
            reading,
            location
        )

        if reading.kind == "omission" then
            if reading.text ~= "" then
                add_record_warning(
                    record,
                    location
                    .. " is classified as an omission "
                    .. "but contains text."
                )
            end
        elseif reading.text == "" then
            reading.valid = false

            add_record_error(
                record,
                location
                .. " is empty and is not classified "
                .. "as an omission."
            )
        end
    end

    if record.valid then
        processing.accepted[
            #processing.accepted + 1
        ] = record
    end
end

function processing.build()
    reset_processing()

    local document = xml.convert(
        buffers.getcontent("tei-data")
    )

    build_witness_registry(document)
    build_apparatus_records(document)

    for _, record in ipairs(
        processing.records
    ) do
        validate_record(record)
    end
end

local function typeset_identifier_list(list)
    if #list == 0 then
        context("none")
    else
        context(
            table.concat(list, ", ")
        )
    end
end

local function resolved_sigla(list)
    local sigla = {}

    for _, witness in ipairs(list) do
        sigla[#sigla + 1] =
            witness.siglum
    end

    return sigla
end

local function typeset_status(valid)
    if valid then
        context("valid")
    else
        context("invalid")
    end
end

local function typeset_messages(
    title,
    messages,
    empty_message
)
    context.subject(title)

    if #messages == 0 then
        context(empty_message)
        return
    end

    context.startitemize()

    for _, message in ipairs(messages) do
        context.startitem()
        context(message)
        context.stopitem()
    end

    context.stopitemize()
end

function processing.typeset_summary()
    context.subject("Processing summary")

    context.starttabulate {
        "|l|r|"
    }

    context.NC()
    context("Declared witnesses")
    context.NC()
    context(#processing.witnesses.in_order)
    context.NC()
    context.NR()

    context.NC()
    context("Apparatus records")
    context.NC()
    context(#processing.records)
    context.NC()
    context.NR()

    context.NC()
    context("Accepted records")
    context.NC()
    context(#processing.accepted)
    context.NC()
    context.NR()

    context.NC()
    context("Errors")
    context.NC()
    context(#processing.errors)
    context.NC()
    context.NR()

    context.NC()
    context("Warnings")
    context.NC()
    context(#processing.warnings)
    context.NC()
    context.NR()

    context.stoptabulate()

    context.blank()

    context.subject("Record status")

    context.starttabulate {
        "|l|l|l|r|"
    }

    context.NC()
    context.bold("Record")
    context.NC()
    context.bold("Status")
    context.NC()
    context.bold("Lemma")
    context.NC()
    context.bold("Readings")
    context.NC()
    context.NR()

    for _, record in ipairs(
        processing.records
    ) do
        context.NC()
        context(record.id)

        context.NC()
        typeset_status(record.valid)

        context.NC()

        if record.lemma then
            context(record.lemma.text)
        else
            context("missing")
        end

        context.NC()
        context(#record.readings)

        context.NC()
        context.NR()
    end

    context.stoptabulate()

    context.blank()

    typeset_messages(
        "Errors",
        processing.errors,
        "No processing errors were detected."
    )

    context.blank()

    typeset_messages(
        "Warnings",
        processing.warnings,
        "No processing warnings were produced."
    )
end

function processing.typeset_records()
    context.subject(
        "Validated intermediate records"
    )

    for _, record in ipairs(
        processing.records
    ) do
        context.subsubject(record.id)

        context.bold("Status: ")
        typeset_status(record.valid)
        context.par()

        if record.lemma then
            context.bold("Lemma: ")
            context(record.lemma.text)
            context.par()

            context.bold(
                "Normalized lemma references: "
            )

            typeset_identifier_list(
                record.lemma.witness_ids
            )

            context.par()

            context.bold(
                "Resolved lemma witnesses: "
            )

            typeset_identifier_list(
                resolved_sigla(
                    record.lemma.witnesses
                )
            )

            context.par()
        else
            context.bold("Lemma: ")
            context("missing")
            context.par()
        end

        for index, reading in ipairs(
            record.readings
        ) do
            context.bold(
                "Reading %s kind: ",
                index
            )
            context(reading.kind)
            context.par()

            context.bold(
                "Reading %s text: ",
                index
            )

            if reading.text ~= "" then
                context(reading.text)
            elseif reading.kind == "omission" then
                context("omission")
            else
                context("empty")
            end

            context.par()

            context.bold(
                "Normalized reading references: "
            )

            typeset_identifier_list(
                reading.witness_ids
            )

            context.par()

            context.bold(
                "Resolved reading witnesses: "
            )

            typeset_identifier_list(
                resolved_sigla(
                    reading.witnesses
                )
            )

            context.par()
        end
    end
end

7.5. Records prepared for ConTeXt

The collection: 

processing.records

contains every apparatus record constructed from the TEI source, including invalid records retained for inspection.

The collection: 

processing.accepted

contains only records that have passed validation and may safely be transmitted to the typesetting layer.

This distinction prevents invalid data from silently reaching the final apparatus while preserving enough information for diagnosis and correction.

A record prepared for ConTeXt now possesses:

  • a stable apparatus identifier;
  • normalized lemma and reading text;
  • explicit editorial categories;
  • normalized witness identifiers;
  • resolved witness objects;
  • documentary order;
  • source-node references;
  • validity information;
  • errors and warnings.

ConTeXt will therefore not need to rediscover the meaning of @wit, search the TEI witness declarations, distinguish omissions from missing data, or decide whether unresolved references should be printed.

The next guide can begin from records whose editorial status has already been made explicit.

7.6. Result of the complete workflow

The complete workflow does not merely transfer information from one notation to another.

It successively changes the epistemic status of the data:

Stage Status of the data
TEI encoding Witnesses and variants are documented through elements, attributes, identifiers, and references.
Extraction The relevant XML structures become accessible to Lua.
Normalization Notational variations are reduced to controlled internal forms.
Reference resolution Character strings become relations to known editorial objects.
Validation Encoded claims are tested against declarations and editorial rules.
Intermediate representation The accepted records form an explicit and reusable body of editorial knowledge.

The final Lua records are therefore not neutral copies of the XML source.

They are the result of documented interpretative operations whose assumptions, successes, and failures can be inspected.

This intermediate representation is what makes a reliable separation between scholarly data processing and typographical composition possible.

At this stage, the data has not yet been typeset, but its editorial status has been made explicit. This is the stable point at which Guide 6 can take over.

8. What Lua should not decide

The processing layer developed in this guide performs substantial interpretative work. It normalizes encoded forms, resolves references, applies validation rules, and constructs editorial records.

This does not mean that every decision should be transferred to Lua.

Some decisions belong to the documentary encoding itself. Others belong to the typographical design of the edition.

Lua should not silently replace either of these layers.

8.1. Lua should not repair the TEI source silently

When the TEI source contains an undeclared witness, an absent lemma, or an ambiguous reading, Lua can detect the problem and report it.

It should not normally invent the missing evidence.

For example, if the source contains: 

<rdg wit="#D">πνοή</rdg>

but witness D has not been declared, Lua may report: 

app-003: unknown witness D in reading 1.

It should not silently create a new witness record for D.

Such a repair would conceal the distinction between documented information and programmatically invented information.

Do not repair silently. A controlled default may be legitimate when the edition explicitly authorizes it, but the intervention should remain visible through a warning, a generated-value flag, or another diagnostic record.

The same principle applies to missing lemmas, absent classifications, or incomplete descriptions. Lua may apply controlled defaults when the editorial policy explicitly permits them, but those defaults should remain visible in the diagnostic state.

8.2. Lua should not erase significant TEI distinctions

The intermediate representation is deliberately smaller than the TEI source, but it should not collapse distinctions that remain editorially significant.

For example, the following situations should not all become an empty string:

  • an omission;
  • a lacuna;
  • unreadable text;
  • absent data;
  • an editorial suppression;
  • an element whose textual content was lost during processing.

A suitable Lua representation should preserve the relevant category: 

{
    kind = "omission",
    text = "",
}

or: 

{
    kind = "lacuna",
    text = "",
}

The reduction from TEI to Lua must therefore be selective rather than destructive.

The processing layer should retain every distinction required by validation, editorial interpretation, or later typesetting.

8.3. Lua should not determine typography prematurely

The Lua records may contain typographically relevant categories, but they should not normally contain fixed visual instructions.

For example, a Lua record may state: 

kind = "omission"

It should not need to state: 

print_text = "om."
font_style = "italic"
separator = "; "

The first value expresses editorial meaning. The other values express one possible typographical realization.

ConTeXt may later render the same omission differently according to:

  • the apparatus layer;
  • the language of the edition;
  • the available horizontal space;
  • the print or screen medium;
  • the conventions of a particular publisher;
  • the typographical hierarchy of the page.

Keeping these decisions in ConTeXt makes it possible to change the appearance without reconstructing the editorial data.

8.4. Lua should not replace editorial judgment

Validation rules can test declared constraints, but they cannot determine every scholarly question.

Lua can establish that:

  • a witness identifier has been declared;
  • a reading contains text;
  • an omission is explicitly classified;
  • the same witness occurs twice in a reference list;
  • a required field is absent.

Lua cannot establish by itself that:

  • a particular reading is philologically preferable;
  • a conjecture is historically plausible;
  • two witnesses belong to the same textual family;
  • a translation adequately represents the source text;
  • an apparatus entry expresses the editor's argument correctly.

The processing layer can make editorial assumptions explicit and test their formal consequences. It cannot replace the scholarly reasoning from which those assumptions arise.

9. Preparing the transition to ConTeXt

The validated Lua records produced in this guide provide a stable boundary between documentary interpretation and typographical composition.

ConTeXt can now receive records whose internal meaning has already been made explicit.

9.1. The contract between Lua and ConTeXt

The processing layer guarantees that accepted records have a predictable structure.

A record passed to ConTeXt may contain: 

{
    id       = "app-001",
    order    = 1,
    valid    = true,

    lemma = {
        text        = "λόγος",
        witness_ids = { "A" },
        witnesses   = {
            {
                id     = "A",
                siglum = "A",
                kind   = "manuscript",
                order  = 1,
            },
        },
    },

    readings = {
        {
            kind        = "reading",
            text        = "λέξις",
            witness_ids = { "B", "C" },
            witnesses   = {
                {
                    id     = "B",
                    siglum = "B",

                    siglum = "C",
                    kind   = "edition",

            },
        },

}

ConTeXt does not need to parse @wit, search <listWit>, or decide whether witness C exists.

It can concentrate on transforming these records into visible typographical structures.

9.2. What ConTeXt will decide

The next guide will determine:

  • how lemmas and readings are formatted;

  • how omissions are represented;
  • how apparatus entries are ordered and grouped;
  • how several apparatus layers are distinguished;
  • how notes are placed and broken across pages;
  • how the same data may be adapted to different layouts.

ConTeXt may also decide whether a description, siglum, or diagnostic value should be printed at all.

These are presentation decisions rather than questions about the validity of the underlying record.

The intermediate representation developed here is not limited to a single apparatus line.

The same processing principles can support records containing:

  • Greek and Latin source texts;

  • several levels of lemmatization;
  • distinct textual, source, and translation apparatuses;
  • bibliographical notes;
  • references to manuscripts, editions, and secondary literature;
  • alignment information between parallel passages;
  • validation reports for each annotation layer.

        latin       = { ... },

        textual     = { ... },

The purpose of the Lua layer is precisely to ensure that ConTeXt receives structured editorial objects rather than unresolved documentary fragments.

10. What this guide has established

This guide has established more than a method for reading TEI XML with Lua. It has shown how documentary data passes through a controlled sequence of interpretative operations before it becomes suitable for typesetting.

10.1. From encoded forms to editorial objects

XML extraction makes elements, attributes, text, and document order accessible. Lua then performs operations that XML parsing alone does not provide:

  • it normalizes notational variants;
  • it classifies lemmas, readings, omissions, and related structures;
  • it resolves identifiers against declared witnesses;
  • it tests editorial constraints;
  • it records errors, warnings, and controlled defaults.

A string such as: 

#A #B

therefore becomes more than accessible text. After normalization and reference resolution, it denotes two known editorial objects whose identity and order can be inspected and reused.

10.2. Normalization and validation are interpretative operations

Normalization defines which differences are treated as significant. For example: 

wit="#A #B"
wit=" #A   #B "
wit="#A #A #B"

may all produce: 

{ "A", "B" }

This equivalence follows an editorial rule: spacing differences and repeated references do not create distinct witness lists.

Validation then tests the normalized records against the declarations and rules of the edition. It determines whether references can be resolved, whether required structures are present, and whether empty or exceptional readings have been classified explicitly.

10.3. Diagnostics preserve the limits of interpretation

An invalid record is not simply discarded. Its normalized fields, unresolved references, source-node connection, and diagnostic messages remain available for inspection.

The processing layer therefore records both what it has established and what it could not establish. Failure becomes traceable rather than silent.

10.4. The intermediate representation is a contract

The validated Lua records form a contract between documentary encoding and typographical composition. They provide ConTeXt with:

  • predictable structures;
  • normalized values;
  • resolved references;
  • explicit editorial categories;
  • separate collections of accepted and rejected records;
  • diagnostic information that has already been produced.

What has changed? TEI remains the authoritative documentary source, but Lua has transformed its relevant structures into inspectable editorial knowledge. ConTeXt can now compose that knowledge without having to reinterpret the XML at every typographical command.

Lua does not replace the TEI document, the editor, or ConTeXt. It mediates between them by making the assumptions, results, and limits of the processing workflow explicit.
